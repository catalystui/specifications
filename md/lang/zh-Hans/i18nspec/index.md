<a id="introduction"></a>
## 引言

**国际化规范（I18NSPEC）**确立了在 CatalystUI 生态系统中评估多语言支持所使用的核心概念、术语和要求。其目的是提供一个清晰标准，用于判断一个系统、服务、框架、应用程序或实现是否提供了足够的语言支持，从而可被视为符合规范。

国际化很重要，因为如果用户界面的基本含义只存在于一种语言中，它就无法清楚地沟通。一个系统在技术上可能能够运行，但如果用户无法理解其标签、说明、控件、设置、警告、错误或核心工作流程，那么该系统就没有为这些用户提供有意义的界面。

本规范并不试图衡量完美的翻译质量、文学风格、文化适配、法律合规或完整的区域本地化。相反，它定义的是最低限度的多语言基础，使用户能够在 CatalystUI 要求的 locale 集合中，有意义地访问并操作系统的关键部分。

更简单地说，I18NSPEC 提出三个主要问题：

1. 用户能否以每种必需语言访问系统的关键部分？
2. 用户能否合理地选择他们理解的语言？
3. 系统是否在不同语言之间保留了足够的含义，使其仍然可用？

> [!IMPORTANT]
>
> I18NSPEC 定义用于验证的国际化要求。它不是针对每种语言的单独规范。每个必需 locale 都按照同一份规范进行检查。

<a id="conformance"></a>
## 符合性

当一个系统针对必需 locale 集合中的每个 locale 满足本文档定义的要求时，该系统即被视为符合 I18NSPEC。

符合规范的系统必须：

1. 支持必需 locale 集合中的每个 locale。
2. 在每个必需 locale 中，为超过 75% 的基本面向用户内容提供翻译。
3. 在每个必需 locale 中，为所有关键面向用户内容提供翻译。
4. 为最终用户提供合理机制，以选择当前 locale。
5. 使用适合该系统的稳定翻译机制。
6. 保留已翻译面向用户内容的基本含义。
7. 避免依赖 fallback 内容来声称翻译覆盖率，除非 locale 等效性在评审中被接受。

系统不需要使用某一种特定实现模式才能符合本规范。它可以使用资源文件、翻译表、locale 感知路由、已编译语言资源、静态本地化页面、运行时语言包、基于数据库的翻译，或其他适合该系统的稳定机制。

验证关注的是实际用户访问能力和基本含义，而不是某一种僵硬的技术架构。

<a id="user-facing-content"></a>
## 面向用户的内容

<a id="user-facing-content-1"></a>
### 面向用户的内容

面向用户的内容是指任何旨在被最终用户感知、阅读、听到、选择、理解或据此采取行动的内容。

面向用户的内容可以包括：

* 导航
* 标签
* 按钮
* 菜单
* 控件
* 标题
* 对话框
* 设置
* 说明
* 提示
* 警告
* 错误
* 确认信息
* 状态消息
* 入门引导文本
* 必需帮助文本
* 语言选择控件
* 核心工作流程内容

面向用户的内容不一定必须是视觉内容。当内容向用户传达含义时，它也可以包括听觉、触觉、符号性或多感官内容。

<a id="essential-user-facing-content"></a>
### 基本面向用户内容

基本面向用户内容是用户为了理解、导航、配置或操作系统的基本行为而合理需要的面向用户内容。

基本面向用户内容可以包括：

* 主导航
* 核心屏幕和视图
* 设置和偏好
* 面向用户的标签
* 面向用户的控件
* 必需说明
* 重要警告
* 重要错误
* 基本提示
* 必需确认消息
* 语言选择控件
* 正常使用所需的核心工作流程

系统不需要翻译每个可选页面、隐藏消息、内部标签或非基本文本才能满足 I18NSPEC。但是，普通基本使用所需的内容必须按照本规范的要求进行翻译。

<a id="critical-user-facing-content"></a>
### 关键面向用户内容

关键面向用户内容是指那些如果被误解，可能阻止有意义使用、造成严重错误，或导致用户在不了解后果的情况下作出重要决定的基本面向用户内容。

关键面向用户内容可以包括：

* 语言选择控件
* 破坏性操作警告
* 账户删除警告
* 付款确认
* 购买确认
* 隐私选择
* 安全警告
* 同意提示
* 必需安全说明
* 必需设置说明
* 必需错误消息
* 到达语言设置所需的核心导航

关键面向用户内容必须为每个必需 locale 翻译。

75% 的基本翻译覆盖率阈值不得被用于让关键内容保持未翻译状态。

<a id="nonessential-content"></a>
### 非基本内容

非基本内容是指用户为了理解、导航、配置或操作系统的基本行为并不合理需要的内容。

非基本内容可以包括：

* 内部标识符
* 源代码名称
* 仅用于调试的字符串
* 面向开发者的实现细节
* 隐藏诊断文本
* 可选营销页面
* 可选支持页面
* 评审范围之外的非基本法律或业务文本
* 不受被评审系统控制的第三方内容

非基本内容可以被翻译，但除非它变成用户理解或操作基本功能所必需的内容，否则它不是 I18NSPEC 符合性所必需的。

<a id="translation-coverage"></a>
## 翻译覆盖率

<a id="essential-translation-coverage"></a>
### 基本翻译覆盖率

基本翻译覆盖率是指针对某个特定 locale，已翻译的基本面向用户内容的数量。

覆盖率应按有意义的面向用户内容单元来评估，而不是按文件大小、字节数、行数、repository 大小或页面数量来评估。

例如，一个控制基本操作的未翻译按钮，可能比一大段不影响普通使用的可选未翻译段落更重要。

翻译覆盖率应根据用户是否能够在被评审 locale 中有意义地理解并操作基本系统来判断。

<a id="coverage-requirement"></a>
### 覆盖率要求

当一个系统在某个 locale 中翻译了超过 75% 的基本面向用户内容时，它即满足该 locale 的翻译覆盖率要求。

当一个系统在必需 locale 集合中的每个 locale 都达到该阈值时，它即满足 I18NSPEC 的覆盖率要求。

在实际评审中，这可以表示为：

| Locale  | 基本翻译覆盖率 | 结果 |
| ------- | -------------- | ---- |
| `en-US` | 100%           | 通过 |
| `es-ES` | 94%            | 通过 |
| `ar-SA` | 78%            | 通过 |
| `ja-JP` | 61%            | 失败 |

覆盖率为 75% 或更低的 locale 不满足覆盖率要求。

覆盖率超过 75% 的 locale 如果存在未翻译的关键面向用户内容，仍可能失败。

<a id="critical-content-requirement"></a>
### 关键内容要求

所有关键面向用户内容都必须为每个必需 locale 翻译。

即使系统满足一般覆盖率阈值，如果一个或多个关键面向用户内容项目缺失、未翻译、具有误导性或无法被有意义地理解，该系统仍可能无法通过 I18NSPEC。

例如，如果一般界面已经翻译，但账户删除警告、购买确认、安全警告或语言选择器仍未翻译，则系统不应被视为符合规范。

<a id="language-selection"></a>
## 语言选择

<a id="active-locale"></a>
### 当前 Locale

当前 locale 是为用户体验当前选择的 locale。

当前 locale 决定应向用户显示、提供或以其他方式传达哪些已翻译内容。

<a id="default-locale"></a>
### 默认 Locale

默认 locale 是用户尚未选择当前 locale 或没有可用用户偏好时所使用的 locale。

系统必须定义一个默认 locale。

默认 locale 应被记录在文档中，或可由评审者合理推断。

<a id="language-selection-mechanism"></a>
### 语言选择机制

符合规范的系统必须为最终用户提供合理方式来更改当前 locale。

语言选择机制必须可用，且不得要求用户：

* 修改源代码
* 使用开发者工具
* 编辑未记录的配置文件
* 安装非官方补丁
* 依赖隐藏行为
* 为普通语言更改联系支持人员

语言选择机制可以通过以下方式提供：

* 应用程序设置
* 账户偏好
* 语言选择器
* 启动提示
* 浏览器设置
* 操作系统设置
* 设备设置
* 其他适合且最终用户可访问的机制

该机制不需要遵循某一种特定设计模式。它必须合理地允许用户选择受支持的语言。

<a id="language-option-labels"></a>
### 语言选项标签

在显示语言选项时，系统应以使用该语言的用户能够理解的方式标识每种语言。

语言选项可以包括：

* 该语言自身的语言名称
* 当前活动语言中的语言名称
* locale 代码
* 区域标签
* 文字系统标签

例如：

```md
English (English) (en-US)
Español (Spanish) (es-ES)
Français (French) (fr-FR)
العربية (Arabic) (ar-SA)
```

具体格式可以有所不同。

其意图是用户应能够识别自己的语言，在可能时理解当前显示的语言名称，并识别相关的 locale 代码。

<a id="fallbacks-and-locale-equivalence"></a>
## Fallback 与 Locale 等效性

<a id="fallback-locale"></a>
### Fallback Locale

Fallback locale 是在当前 locale 的已翻译内容不可用时使用的 locale。

Fallback locale 可以帮助保持可用性，但 fallback 内容不会自动被视为当前 locale 的已翻译内容。

例如，如果系统设置为 `es-MX`，但由于缺少西班牙语翻译而显示 `en-US` 文本，那么该英文文本可以作为 fallback 有用，但不应被计入西班牙语翻译覆盖率。

<a id="fallback-behavior"></a>
### Fallback 行为

符合规范的系统可以在本地化内容不可用时使用 fallback 行为。

Fallback 行为应避免损坏、空白或误导性输出。

Fallback 行为不得被用于虚假声称某个必需 locale 的翻译覆盖率。

如果 fallback 行为过多、令人困惑、未记录，或导致基本内容在某个必需 locale 中看起来未被翻译，系统可能会收到警告或失败结果。

<a id="locale-equivalence"></a>
### Locale 等效性

当一个翻译能够合理服务于多个 locale，且不会阻止基本理解或操作时，即发生 locale 等效性。

例如，如果基本含义对 `en-US`、`en-GB` 和 `en-IN` 的用户都保持清楚，一个系统可以为这些 locale 使用同一份英文翻译。

当区域差异较小且不会实质影响基本可用性时，locale 等效性可以在评审中被接受。

当缺失某个 locale 会造成有意义的混淆、遗漏重要区域术语、破坏基本行为或阻止用户理解系统时，不得使用 locale 等效性。

例如，系统不应仅因为无关语言共享书写方向、地理区域、文字系统家族或宽泛文化类别，就假定它们等效。

Locale 等效性是一项评审判断，而不是自动规则。

<a id="implementation-requirements"></a>
## 实现要求

<a id="stable-translation-mechanism"></a>
### 稳定的翻译机制

符合规范的系统必须使用适合被评审系统的稳定翻译机制。

稳定的翻译机制应允许翻译内容被维护、更新、评审和扩展，而不依赖脆弱或未记录的行为。

稳定的翻译机制可以包括：

* 资源文件
* 翻译表
* locale 感知路由
* 已编译语言资源
* 静态本地化页面
* 运行时语言包
* 基于数据库的翻译
* 其他已记录的翻译结构

系统应避免以会阻止必需翻译支持的方式 hardcode 基本面向用户内容。

<a id="preservation-of-meaning"></a>
### 含义保留

当用户能够合理理解与源语言用户相同的基本说明、标签、警告、控件、设置或工作流程时，翻译即保留了含义。

翻译不需要与源内容逐字一致。

为了在目标语言中传达相同的基本含义，翻译可以在必要时改变词序、语法、句子结构、习语、语气或措辞。

如果翻译具有误导性、不完整、无意义、被机器破坏，或以影响基本使用的方式与源内容有实质差异，则它可能无法通过评审。

<a id="direction-sensitive-languages"></a>
### 对文字方向敏感的语言

一些必需 locale 通常使用从右到左的文字方向。

符合规范的系统不得因为当前 locale 使用不同文字方向，就阻止基本翻译内容被阅读、理解、选择或据此采取行动。

系统应为对文字方向敏感的语言保留可读的顺序、标点行为以及控件关联。

完整的视觉打磨、排版质量、无障碍行为和布局细化可能需要单独评审。但是，基本翻译内容必须保持有意义的可用性。

<a id="locale-sensitive-values"></a>
### 对 Locale 敏感的值

对 locale 敏感的值是指其含义或可读性可能因语言、地区、文字系统或文化而变化的值。

对 locale 敏感的值可以包括：

* 日期
* 时间
* 数字
* 货币
* 度量单位
* 复数形式
* 语法性别
* 排序顺序
* 地址格式
* 电话号码格式

I18NSPEC 不要求完整本地化每个对 locale 敏感的值，除非该值对理解或操作系统是基本必需的。

当对 locale 敏感的值是基本必需时，系统应以当前 locale 用户能够合理理解的方式表示它们。

<a id="verification"></a>
## 验证

<a id="within-spec"></a>
### 符合规范

当 CatalystUI Team 已评审系统，并认为可以合理得出该系统满足 I18NSPEC 的结论时，该系统即被视为符合规范。

系统可以在以下情况下符合规范：

* 支持每个必需 locale
* 每个必需 locale 中超过 75% 的基本面向用户内容已翻译
* 每个必需 locale 中所有关键面向用户内容已翻译
* 用户能够合理选择当前 locale
* fallback 行为不会虚假声称翻译覆盖率
* 如果使用 locale 等效性，则它是合理且已记录的
* 已翻译内容保留基本含义

即使某些非基本内容仍未翻译，系统也可以符合规范。

即使翻译并不完美，只要基本含义得到保留且满足本规范要求，系统也可以符合规范。

<a id="warnings"></a>
### 警告

当系统看起来满足 I18NSPEC，但包含应记录的问题时，可以发出警告。

警告可以包括：

* 少量未翻译的非基本内容
* 各 locale 之间术语不一致
* 不完美但可理解的翻译
* 可接受但应记录的 locale 等效性
* 有限的 fallback 行为
* 部分翻译的可选页面
* 不阻止基本使用的文字方向敏感布局问题
* 可理解但不理想的 locale 敏感值

警告不一定阻止验证。

<a id="failures"></a>
### 失败

当系统未满足 I18NSPEC 的一个或多个必需条件时，即发生失败。

失败可以包括：

* 缺少对必需 locale 的支持
* 某个必需 locale 的基本翻译覆盖率为 75% 或更低
* 未翻译的关键面向用户内容
* 没有合理的语言选择机制
* 语言选择要求修改源代码
* 语言选择要求使用开发者工具
* 翻译加载损坏
* 误导性的 locale 声明
* 过度 fallback 行为
* 没有有效 locale 等效性却将 fallback 内容计为已翻译内容
* 对文字方向敏感的内容不可读或不可用
* 一个或多个必需 locale 中无法使用基本工作流程

失败会阻止验证，直到问题被解决。

<a id="verification-validity"></a>
### 验证有效性

I18NSPEC 验证只适用于系统在验证签发时被评审的状态。

只要系统保留已验证的国际化基础，它就可以在后续更新中保持验证。

轻微措辞变更、新增翻译、改进翻译以及普通内容更新不会自动使验证失效。

如果系统出现以下情况，可能需要新的评审：

* 移除必需 locale 支持
* 破坏语言选择
* 大幅降低基本翻译覆盖率
* 让新的基本工作流程未翻译
* 用 fallback 内容替换已翻译内容
* 以影响已验证行为的方式改变翻译架构
* 引入会改变已评审范围的重大面向用户更改

换句话说，改进翻译支持通常是可以的。

破坏已验证的多语言基础可能需要重新评审。

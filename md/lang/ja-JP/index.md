# プログラミング言語向け CatalystUI Verified

プログラミング言語向け CatalystUI Verification ドキュメントへようこそ。

**プログラミング言語向け CatalystUI Verified** は、あるプログラミング言語が CatalystUI チームによってレビューされ、CatalystUI 互換システムを表現するために必要な基礎的なデータ表現と関係構造を提供できると判断されたことを示します。

この検証は、プログラミング言語の一般的な順位付けではありません。ある言語が別の言語より優れている、速い、簡単である、新しい、人気がある、あるいは楽しいかどうかを決めるものではありません。代わりに、CatalystUI Verification に必要な仕様に対して、その言語が安定した実用的な土台を提供できるかどうかを確認します。

より簡単に言えば、この検証は「そのプログラミング言語が、CatalystUI の依存する基本的なデータと関係を忠実に表現できるか」を問うものです。

## 目的

プログラミング言語は、すべての CatalystUI 実装の下にある表現上の土台です。フレームワーク、ライブラリ、ランタイム、アプリケーション、サービスが CatalystUI Stack に従う前に、それを構築するために使われる言語は、このモデルが依存する基礎概念を表現できなければなりません。

プログラミング言語において、これは主に次の二つを意味します。

1. その言語は基礎データを表現できなければなりません。
2. その言語はデータ間の基礎的な関係を表現できなければなりません。

これらの観点は、CatalystUI の基礎仕様によって定義されます。FDEFSPEC は期待される基礎データ表現を定義します。FRELSPEC は、それらの表現間に期待される基礎関係を定義し、collections、memory relationships、operations、threading relationships、composites を含みます。

検証済みのプログラミング言語は、CatalystUI が必要とする基本概念に対して、壊れやすく、不明瞭で、不安定な回避策に頼らずに CatalystUI 互換システムを構築できるだけの明確さと制御を開発者に与えます。

## Verification の意味

プログラミング言語は、このセクションに記載された仕様に照らしてレビューされ、within spec と判断されたときに **CatalystUI Verified** になります。

Programming Language Verification では、適用される仕様によって定義された基礎要件をその言語が表現できるかどうかに焦点を当てます。これは、その言語自体が CatalystUI の実装であるという意味ではありません。CatalystUI 互換実装を構築するための適切な土台を、その言語が提供するという意味です。

ある言語が、別の言語とまったく同じ方法でこれらの要件を満たす必要はありません。言語ごとに、構文、型システム、標準ライブラリ、コンパイラ、ランタイム、設計パターンは異なります。CatalystUI Verification は、必要な概念が明確に、信頼できる形で、一貫して表現できる限り、それらの違いを許容します。

## “Within Spec” の意味

プログラミング言語が **within spec** と見なされる場合、それは CatalystUI チームがその言語を手動でレビューし、適用される仕様に記述された必要な振る舞いをその言語内で表現できると結論づけることが妥当だと判断したことを意味します。

これは、単一の固定された実装パターンを要求するものではありません。言語は、組み込みプリミティブ、標準ライブラリ機能、コンパイラの振る舞い、ランタイムの振る舞い、文書化された保証、またはその言語に適した他の安定した仕組みによって要件を満たすことができます。

検証が扱うのは、仕様の意味を実用的に表現し保持できる能力であり、その言語が仕様本文とまったく同じ名前、構造、構文、内部設計を使うかどうかではありません。

## この Verification が存在する理由

CatalystUI は、人間とコンピュータがどのように相互作用するかを、明確さ、一貫性、忠実な表現を中心に設計しています。プログラミング言語が重要なのは、開発者が現実的に何を表現できるか、それらのシステムをどれだけ安全にモデル化できるか、そして上位レベルの実装をどれだけ明確に構築できるかを決めるからです。

ある言語が必要な基礎概念を安定した方法で提供できない場合、上位レベルの CatalystUI 実装は信頼しにくくなります。開発者は、本来なら最初から信頼できるべき考えを表現するために、不明瞭な抽象化、予測しにくい振る舞い、壊れやすい依存関係、不要な書き直しへ追い込まれる可能性があります。

Programming Language Verification は、CatalystUI の作業に十分強固な土台を提供する言語を識別するために存在します。これにより、開発者、言語設計者、組織は、その言語が CatalystUI 互換システムの構築に適しているかどうかをより明確に理解できます。

## 言語が Verified になる方法

**プログラミング言語向け CatalystUI Verified** になるには、その言語がこのセクションに記載された仕様に照らしてレビューされる必要があります。

一般的な手順は次のとおりです。

1. 適用される CatalystUI 仕様を特定します。
2. その言語を、必要な各仕様に照らしてレビューします。
3. CatalystUI チームが、その言語が仕様の意図と要件を満たすかどうかを判断します。
4. その言語が within spec と判断された場合、CatalystUI Verification を付与できます。
5. 検証後、その言語は [Verified Languages](/verified/) ページに掲載できます。

レビューでは、公式の言語ドキュメント、標準ライブラリの振る舞い、コンパイラの振る舞い、ランタイムの振る舞い、実装例、テストケース、およびその言語が要件を満たすか判断するために必要なその他の証拠を考慮できます。

コンパイラとランタイムの振る舞いは、それがその言語の一般的かつ公式な利用方法の一部である場合、レビュー中に考慮できます。ただし、プログラミング言語を検証することは、その言語のエコシステム内にあるすべてのコンパイラ、ランタイム、パッケージ、フレームワーク、ライブラリ、アプリケーション、ツールを自動的に検証することではありません。

## 適用される仕様

このセクションに記載された仕様は、Programming Language Verification に使用される要件を定義します。

プログラミング言語については、現在の有効な土台は次の仕様カテゴリを中心にしています。

* **FDEFSPEC**: 基礎データ表現を定義します。
* **FRELSPEC**: データ表現間の基礎関係を定義します。

これらの仕様は合わせて、プログラミング言語が CatalystUI 互換システムを表現するために必要な最小限の土台を確立します。

より専門化された検証カテゴリのために、将来追加の仕様が導入される可能性があります。それらの仕様は、上位レベルの実装、プラットフォーム、アクセシビリティ、国際化、フレームワーク、サービス、ランタイム要件を定義する場合があります。ただし、それらの後続仕様はこの土台を置き換えるのではなく、その上に構築されます。

プログラミング言語は、このカテゴリで必要な仕様を満たすことで検証済みになります。無関係な実装固有の要件は、それらが Programming Language Verification に追加されない限り、満たすことを期待されません。

## Verification の範囲

プログラミング言語向け CatalystUI Verification は、レビューされた状態のプログラミング言語に適用されます。

検証済みの言語は、CatalystUI 互換開発に適した土台を提供します。それは、その言語で書かれたすべてのプロジェクトが CatalystUI に正しく従うことを保証するものではなく、周辺エコシステムを自動的に検証するものでもありません。

個別のツール、ライブラリ、フレームワーク、ランタイム、アプリケーション、サービス、実装は、要求される検証カテゴリに応じて、それぞれ独自のレビューを必要とする場合があります。

したがって、Programming Language Verification は土台の確認として理解されるべきです。これは、その言語が必要な概念を表現できることを確認します。その言語のすべての利用が、それらの概念を正しく適用していることを確認するものではありません。

## Verification の有効性

CatalystUI Verification は、検証が発行された時点でレビューされたプログラミング言語の状態にのみ適用されます。

多くの言語は複数のバージョン間で互換性を維持するため、プログラミング言語は特別なケースとして扱われます。言語は、元のレビューが依存していた機能、プリミティブ、表現、振る舞いとの後方互換性を維持する限り、後続バージョンでも検証を保持できます。

新しい言語機能だけで検証が無効になることはありません。将来のバージョンが、検証済みの土台を削除、破壊、または大きく変更した場合にのみ、新しいレビューが必要になることがあります。

言い換えると、言語を拡張することは通常問題ありません。検証済みの土台を壊す場合は、レビューが必要になる可能性があります。
